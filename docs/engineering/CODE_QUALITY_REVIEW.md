# 코드 품질 점검: 작업 알림과 실패 경계

2026-09-11 · 범위: Planner의 편집·검사·검색·저장·문의 문구 복사, 공통 UI 및 계층 의존성. 전체 외부 공급자 정확도나 운영 부하를 검증한 보고서는 아니다.

## 확인한 구조

- 규정 판정과 일정 계산은 순수 domain에 있고, application은 외부 공급자 포트에 의존한다. Next 라우트·외부 어댑터와 UI가 도메인을 구현하지 않는다.
- Planner의 Zustand 인스턴스와 QueryClient는 화면마다 생성한다. 서버 전역 사용자 상태를 공유하지 않고 SSR 날짜 초기값을 전달한다.
- 편집·조회·저장 책임은 별도 훅/스토어에 있고, 공통 shadcn/Radix 컴포넌트는 업무 판단을 하지 않는다. 추가 범용 클래스나 버튼별 HOC는 필요하지 않았다.

## 발견 사항과 수정

| 발견 | 영향 | 수정 |
|---|---|---|
| notice/error 문자열만으로 결과를 표현 | 동일한 작업의 반복을 새 알림과 구분하기 어려움 | 일회성 타입 이벤트, 변경 구독, 공통 알림 HOC |
| 문의 문구 복사 catch가 일반 notify 사용 | 복사 실패가 성공/안내와 섞임 | 성공과 오류 콜백 분리, 오류는 화면에도 유지 |
| 응답 처리에서 revision만 확인 | 화면 이탈로 취소한 요청도 결과 처리 경로에 들어갈 수 있음 | AbortSignal 상태까지 확인 후 결과·오류 반영 |
| 클라이언트가 모든 응답을 JSON으로 가정 | 프록시 HTML 장애에서 영문 SyntaxError 노출 | 파싱 오류를 한국어 재시도 안내로 변환, 취소 오류는 보존 |
| 방문지 제거를 JSX에서 직접 배열 갱신 | 액션 피드백과 고정/범위 검사 누락 가능 | usePlanner의 remove 액션으로 이동 |
| 닫히는 토스트 ID 재사용(새 테스트에서 발견) | 닫은 직후 같은 작업을 하면 새 알림 소실 | 화면별 Toaster, 작업별 새 ID, 직전 알림만 해제 |

도메인·사용 사례의 UI/Sonner import와 기능의 직접 Sonner 호출은 ESLint로 차단한다. shared notification boundary도 업무 코드에 의존할 수 없도록 검사한다. 이벤트를 저장 계약에 포함하지 않는다.

## 검증 범위

단위 검사는 기존 순수 판정·일정·복구·설정·스토어 검사에 반복 이벤트/이전 응답 무알림 회귀를 추가한다. Playwright는 실제 화면에서 저장 반복과 키보드 닫기, 재진입, 인쇄, 입력/프록시/클립보드 오류, 재시도 완료를 확인한다. 직접 개발·code-server 프록시·운영 빌드 및 데스크톱/모바일의 실행 결과는 [구현 기록](../delivery/IMPLEMENTATION_STATUS.md)에 기록한다.

실 API 연결·LLM 추출 품질, Firestore/배포 연결 및 장시간 부하 검증은 별도 후속 작업이다. 이번 점검의 통과를 해당 항목의 완료로 간주하지 않는다.
