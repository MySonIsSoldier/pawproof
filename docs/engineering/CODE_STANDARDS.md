# 코드 작성과 검증 원칙

기준일: 2026-09-10\
적용 범위: 앞으로 작성하는 PawProof 코드. 기술 선택은 [스택 결정](STACK_DECISION.md), 의존성 경계는 [아키텍처](ARCHITECTURE.md)를 따른다.

## 단일 책임과 명확한 이름

함수와 모듈은 같은 이유로 바뀌는 일을 모은다. HTTP 응답 처리, 규정 해석, 판정, DB 저장, 화면 문구를 하나의 함수에 넣지 않는다. 파일 길이만으로 쪼개거나 임의의 줄 수를 품질 기준으로 삼지 않는다.

- `evaluateWeightRule`, `recalculateArrivalTimes`처럼 동작을 드러내는 이름을 쓴다.
- 입력·출력·실패 조건을 타입과 계약으로 표현한다.
- 중복을 줄이되 서로 다른 정책을 너무 일찍 범용화하지 않는다.
- 예외 조건의 이유와 외부 API의 특이사항은 주석으로 남긴다. 코드가 말하는 사실을 다시 설명하는 주석은 줄인다.
- 공급자 교체에 대비한 인터페이스는 외부 경계에 둔다. 모든 값을 클래스화하지 않는다.

## 타입과 데이터 검증

TypeScript `strict`를 사용하고 외부 입력은 `unknown`부터 검증한다. API 응답이나 LLM 결과를 `as Policy`로 단언해 안전하다고 간주하지 않는다.

체중 단위, 허용 마릿수, 이하·미만, AND·OR, 적용 구역, 날짜·시간대와 근거를 명시적으로 표현한다. `null`, 누락, 빈 문자열, 제한 없음은 서로 다른 의미로 다룬다. 상태와 사유는 구별 가능한 유니온·코드로 관리하고 UI 문구와 분리한다.

서버 비밀은 서버 전용 모듈에서 읽고, 공개 설정은 허용 목록으로만 내보낸다. 환경 파싱은 앱 곳곳의 `process.env` 참조 대신 설정 계층에서 수행한다.

## 실패와 비동기 처리

예상 가능한 실패는 명확한 오류 종류로 전달한다. 공급자 시간 초과, 쿼터 초과, 응답 스키마 오류, 규정 불명확, 유효 대체 후보 없음은 같은 오류가 아니다.

- `catch`에서 빈 배열이나 이용 가능 상태를 반환하지 않는다.
- 외부 호출에는 시간 제한·취소·총 요청 예산을 둔다.
- 일시 오류만 제한적으로 재시도한다. 인증 실패·잘못된 입력을 재시도하지 않는다.
- LLM 재시도는 중복 비용을 만들 수 있으므로 별도 예산에 포함한다.
- 전역 메모리 캐시·인메모리 카운터가 서버리스 전체 인스턴스에서 공유된다고 가정하지 않는다.
- 원문·파생 규정의 요청 간 캐싱은 [데이터 전략](../data/DATA_STRATEGY.md)의 허용 범위가 확정된 뒤 적용한다.

## 프론트엔드 품질

Server Component를 기본으로 하되 상호작용 경계를 작게 둔다. 지도 등 큰 라이브러리는 필요한 화면에서만 불러온다. React 상태로 충분한 화면에 전역 저장소를 먼저 도입하지 않는다.

로딩·부분 실패·후보 없음·입력 변경 후 재검증 필요를 화면 상태로 설계한다. 네 판정 상태를 색상만으로 구분하지 않고 텍스트·아이콘·설명을 함께 제공한다. 폼 label, 키보드 조작, 모바일 터치 영역을 확인한다.

경로 처리에는 [개발 환경의 유틸 계약](DEVELOPMENT_ENVIRONMENT.md)을 사용한다. 컴포넌트에 `/proxy/3000`, `/absproxy/3000`, 운영 도메인을 하드코딩하지 않는다.

시각 디자인은 사용자가 제공할 레퍼런스에 맞춰 정한다. 데이터 출처, 확인 필요, 실패 사유처럼 제품 판단에 필요한 정보는 디자인 변경으로 숨기지 않는다.

## 테스트와 완료 기준

| 범위 | 우선 검증 |
|---|---|
| 순수 도메인 | 체중 경계, 여러 마리, AND/OR, 구역, 충돌·누락, 도착·마감 시각 |
| 추출·공급자 어댑터 | 잘못된 JSON·단위·근거, 타임아웃, 쿼터 오류, 응답 필드 변화 |
| 사용 사례 | 한 장소 실패의 부분 결과, 대체 후 전체 재검증, 고정 일정 유지 |
| 경로·환경 | 로컬·프록시·배포 URL, 중복 접두사, 비밀의 클라이언트 유출 방지 |
| 브라우저 | 핵심 한 코스의 입력 → 판정 → 근거 → 대체 → 준비표 |

단위 테스트는 외부 유료 API를 호출하지 않는다. 실제 API 연결 검증은 명시적으로 분리하고, 키·원문 보관 범위를 지킨다. 합성 fixture는 가상 데이터라고 표시한다. 원본 규정 평가 자료는 보관 허용 범위를 확인한다.

변경에 맞는 타입 검사·린트·테스트·빌드를 수행하고 실제 결과를 기록한다. 새로운 실패나 변경이 없으면 같은 검사를 반복하지 않는다. 단순한 문서 변경에 앱 테스트를 만들지 않고, 구현을 복사한 테스트나 임의의 100% 커버리지 목표도 두지 않는다.

## 협업과 변경 관리

공개 Organization 저장소에서 작은 작업 단위로 변경을 검토한다. PR에는 해결한 사용자 문제, 바뀐 동작, 관련 검증과 남은 제약을 쓴다. GitHub 소스 협업 권한과 호스팅 관리 권한은 별도로 관리한다.

판정 기준을 바꾸면 [판정 문서](../product/RULES_AND_RECOVERY.md)와 사례를, 환경 설정을 바꾸면 [개발 환경 문서](DEVELOPMENT_ENVIRONMENT.md)를 함께 갱신한다. 결정과 미결 사항은 [히스토리](../history/DECISION_HISTORY.md)에 남긴다.

현재 저장소에는 `AGENTS.md`, `docs/plan.md`, 활성 변경 제안(CP) 체계가 없다. 별도 체계를 있다고 가정하지 않고 이 문서 묶음을 기준으로 관리한다. 문서 정리 요청만으로 커밋·푸시·배포 완료를 선언하지 않는다.
