# 구현·검증·제출 계획

기준일: 2026-09-10\
현재 상태: 기획 문서화 단계. 아래 항목은 구현 완료 목록이 아니다.

## 제출 버전의 완료 기준

실제 API를 사용해 **프로필 입력 → 코스 구성 → 판정·근거 확인 → 해결안 선택 → 전체 재검증 → 출발 준비표**를 끝까지 사용할 수 있어야 한다.

| 우선순위 | 항목 | 완료 기준 |
|---|---|---|
| 필수 | 반려견별 프로필 | 여러 마리의 조건을 각각 반영하고 전체 마릿수 제약도 평가 |
| 필수 | 당일 코스 구성 | 3~5개 방문지의 선택·삭제·순서·체류시간 변경 |
| 필수 | 실제 API 기반 판정 | 네 상태, 정보 누락·충돌·추출 실패 처리 |
| 필수 | 근거 보기 | 원문·출처·확인 시점과 판정 이유 연결 |
| 필수 | 구역·이용 방식 구분 | 실내 제한을 장소 전체 제한으로 잘못 확대하지 않음 |
| 필수 | 대체 후보 비교·적용 | 같은 목적, 동반 조건, 시간 조건과 이동시간 변화 표시 |
| 필수 | 전체 코스 재검증 | 교체 이후 방문지의 도착 시각과 조건 재평가 |
| 필수 | 준비사항·문의 문구 | 코스 규정 및 미확인 항목에 연결 |
| 필수 | 모바일·비로그인 체험 | 심사위원이 바로 핵심 과업 수행 가능 |
| 필수 | 장애·빈 결과 처리 | API 실패·유효 후보 없음이 오판으로 이어지지 않음 |
| 여유 시 | 동일 장소 해결안 자동 비교 | 원문이 뒷받침하는 준비·구역·시간 변경안 비교 |
| 여유 시 | 공유·출발 전 재검증 | 저장 시점과 현재 상태를 구분하고 재조회 |

숙박·예약 결제·커뮤니티·자동 전화·날씨 대응·자유대화 챗봇·전국 규정 수집·앱 스토어 출시는 초기 범위 밖이다.

기술 우선안은 Next.js + Vercel Hobby + Firestore Spark다. 공개 Organization 저장소, 무료 운영 요구, code-server 개발 환경을 반영했다. 상세 선택 이유와 Cloudflare·OCI 대안은 [스택 결정](../engineering/STACK_DECISION.md)을 따른다. 계정 연결과 실행 검증 전이므로 배포 완료로 간주하지 않는다.

## 역할 분담

| 담당 | 주요 역할 |
|---|---|
| 사용자·팀장 | 기획·PM, 데이터 연결, 규정 추출·판정, 대체 계산, 백엔드, 배포·운영 |
| 생활관 선임·팀원 | UX/UI, 프론트엔드·모바일 웹, 규정 교차 검수, 사용자 테스트, 시연·제출 이미지 |
| 공동 | 판정 상태의 의미, 실제 근거 사례, 대표 코스, 평가 기준, 제출 자료 정합성 |

과거 역할 분담에 있던 PWA는 필수 설치 기능을 뜻하지 않는다. 우선 웹의 핵심 기능을 완성한다.

## 개발 기반의 첫 완료 기준

- [개발 환경 계약](../engineering/DEVELOPMENT_ENVIRONMENT.md)에 따라 로컬 루트·code-server·배포 루트의 페이지·자산·API를 검증한다.
- 환경 파싱·URL 유틸을 먼저 구현하고 개발 프록시 경로가 컴포넌트에 퍼지지 않도록 한다.
- 공개 Org의 두 사람 협업과 실제 배포 흐름을 확인한다.
- 서버 전용 Firestore 접근과 현재 KTO 호출을 작은 진단 흐름으로 확인한다.
- [호스팅·비용 계획](../operations/HOSTING_AND_COST.md)에 따라 외부 API 사용량과 시간 예산을 측정한다.
- 디자인 참고자료는 사용자가 제공한다. 레퍼런스 확정 전에도 환경·데이터·도메인 로직 작업은 진행 가능하다.

새 플랫폼 비교가 핵심 개발을 잠식하지 않도록 초기 검증은 반나절을 목표로 한다. 실제 제약이 발견되었을 때만 대안을 검증한다.

## 데이터 점검에서 진행 여부 판단

첫 점검에서 다음을 확인한다.

- 실제 공사 API가 현재 승인 계정으로 동작하는가.
- 권역 안에 식사·휴식·관광 목적을 연결할 수 있는 후보가 있는가.
- 주요 문제 방문지를 바꿀 유효 후보를 확보할 수 있는가.
- 체중·마릿수 정보가 부족한 장소의 확인 경로가 있는가.
- 데이터 저장·호출량 제약 안에서 제출 버전을 운영할 수 있는가.

밀도가 부족하면 지역·업종 범위를 조정한다. 정보 부족을 추측으로 메우거나 잘 작동하는 예시만 전체 성능처럼 소개하지 않는다.

## 품질 평가

### 지표

| 지표 | 측정 내용 |
|---|---|
| 잘못된 이용 가능 판정 | 사람 기준 불가·미확인 사례를 앱이 이용 가능으로 처리한 건수와 비율 |
| 근거 있는 결론의 범위 | 전체 평가 사례 중 충분한 근거로 결론을 낸 비율 |
| 불확실성 처리 | 누락·충돌·모호함을 확인 필요로 적절히 분류했는지 |
| 대체안 유효성 | 반려견·시간·방문 목적·고정 일정 조건을 함께 만족하는지 |
| 과업 완료 시간 | 코스 확인과 수정까지 걸리는 시간 |
| 남은 확인 부담 | 사용 후 직접 찾아보거나 문의할 항목 수 |
| 운영 품질 | 실제 코스 검증 응답시간, API 오류 및 복구 결과 |

모든 사례를 확인 필요로 처리해 오판을 줄이는 방식은 충분하지 않다. 오판과 판정 가능 범위를 함께 보고한다.

### 평가 방법

1. 업종·조건 표현·수정 시점이 다양한 원문으로 평가 사례를 구성한다.
2. 두 사람이 원문, 적용 조건, 기대 상태를 교차 검수하고 의견 차이를 기록한다.
3. 개발에 사용한 사례와 최종 평가 사례를 분리한다.
4. 제안 규모로 실제 보호자 5~8명의 과업 테스트를 진행한다.
5. 일반 검색 방식과 PawProof 사용 시 시간·조건 누락을 비교한다.
6. 유사 난도의 다른 코스나 순서 교차로 학습효과를 줄인다.
7. 가능하면 핵심 장소 몇 곳의 규정을 실제로 재확인한다.

테스트 참가자·장소 재확인은 아직 확보·수행하지 않았다. 측정 결과에는 표본, 수행일, 방법, 한계를 남긴다. 실제 여행 추적 없이 입장 거부 감소율이나 완주율을 주장하지 않는다.

### 의미 있는 동작 검증 사례

- 10kg 이하와 미만의 경계.
- 반려견별 체중 제한과 일행 전체 마릿수 제한.
- 이동장 OR 유모차, 이동장 AND 입마개.
- 실내·실외의 서로 다른 정책.
- 같은 문구의 중복 출처 처리.
- 누락·상충 원문·추출 실패·외부 API 오류.
- 대체로 다음 장소의 입장 마감을 넘는 경우.
- 고정된 방문지를 유지할 유효 대체안이 없는 경우.
- 한 문제를 해결해도 다른 미확인 조건이 남는 경우.

구현 코드를 그대로 반복하는 테스트보다 오판과 일정 실패를 방지하는 사례를 우선한다.

## 약 3분 시연 흐름

1. 반려견과 방문지 4곳이 담긴 실제 코스를 연다.
2. 체중 또는 마릿수를 변경하고 다시 검사한다.
3. 바뀐 상태와 관련 원문을 보여준다.
4. 준비사항 또는 대체 후보를 선택한다.
5. 이후 일정과 준비표가 갱신되는 것을 보여준다.
6. 남은 확인 필요 항목과 문의 내용을 연다.

설명용 가상 예시:

| 방문지 | 최초 문제 | 해결 |
|---|---|---|
| A 관광지 | 조건 충족 | 유지 |
| B 식당 | 체중 제한 위반 | 같은 식사 목적의 적합 식당으로 교체 |
| C 카페 | 이동장 준비 필요 | 사용자 준비 상태 기록 |
| D 체험시설 | 두 마리 이용 여부 미확인 | 해당 조건만 문의 |

`방문지 1곳 변경 · 예상 이동시간 8분 증가 · 준비 1건 · 확인 1건`은 화면 설명용 수치다. 실제 시연은 검증한 장소와 계산 결과를 사용한다.

## 제출 자료 구성

- 대표 이미지: 코스 검증 결과와 변경 전후 차이.
- 상세 이미지: 프로필, 코스 판정, 근거 상세, 대체 후보 비교, 최종 준비표 중 3~5장.
- 기능설명서는 [제품 기획의 해시태그](../product/PRODUCT_PLAN.md#해시태그와-구현-증거)와 실제 기능을 일치시킨다.
- 실제 사용하는 API만 기재하고 응답 데이터가 판정에 기여하는 과정을 설명한다.
- 성과 수치는 측정값만 기재한다.
- 공식 양식, 서비스 URL, 로그인 방식, 키 제출 정보, 최종 팀원, 지정과제를 대조한다.
- 문서·공개 화면에 운영 인증키가 포함되지 않도록 확인한다.

## 제출 후 운영

- 서비스 URL, API 권한·쿼터·실패율을 점검한다.
- 정책이 바뀌면 현재 근거를 재조회하고 판정에 반영한다.
- 제출 당시 기능과 자료의 관계를 유지하고 변경 시 이력을 남긴다.
- 최종 발표에서는 기능 개수보다 실제 과업 결과와 평가 근거를 중심으로 설명한다.
