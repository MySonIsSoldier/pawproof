- 재사용 가능한 [단위 테스트](../../tests/unit/app-config.test.ts)와 [브라우저 테스트](../../tests/e2e/environment.spec.ts).

HMR 검증에서는 컴포넌트 문구를 변경한 뒤 WebSocket 통신·화면 갱신·기존 클라이언트 상태 유지를 확인하고 파일을 복원했다. 테스트가 변경하는 파일은 테스트 실행 중 편집하지 않는다. 모드별 제외는 의도한 검사 범위 차이이며 미해결 실패가 아니다.

`pnpm dev`가 Git에서 제외한 `.env.development.local`을 먼저 읽고 3000번 프록시 개발 모드로 시작하는 것도 확인했다. 파일에는 개발 프로필만 있고 서비스 인증키는 없다.

## 검증 환경과 재실행

OCI 컨테이너의 Node.js 24.13.0, Linux ARM64에서 수행했다. 기존 IDE의 외부 인증 세션 대신 설치된 **code-server 4.127.0 바이너리**로 루프백에 임시 프록시를 실행하여 재현했다. 외부 Coolify·HTTPS·로그인 세션까지 검증한 결과로 일반화하지 않는다.

현재 컨테이너에는 Corepack 기본 캐시 쓰기 권한과 Chromium의 `libxkbcommon.so.0`가 없었다. 초기 검증에는 `/tmp/pawproof-corepack`, `/tmp/ms-playwright`, `/tmp/pawproof-browser-libs`를 사용했다. 이후 `.corepack.env`를 추가해 **일반 pnpm 명령이 프로젝트의 `.cache/corepack`을 사용하도록 해결**하고 버전 확인·lockfile 기반 설치를 검증했다. 시스템 권한은 변경하지 않았다. 브라우저의 임시 경로는 환경 정리 후 없어질 수 있으며 앱의 배포 의존성은 아니다.

일반적인 브라우저 의존성이 설치된 환경의 실행 명령은 [루트 README](../../README.md)를 따른다. 이번 컨테이너에서 사용한 환경 설정은 다음과 같다.

```bash
export COREPACK_HOME=/tmp/pawproof-corepack
export PLAYWRIGHT_BROWSERS_PATH=/tmp/ms-playwright
export LD_LIBRARY_PATH=/tmp/pawproof-browser-libs/usr/lib/aarch64-linux-gnu

pnpm test:e2e
# 8444번에 임시 code-server 프록시가 실행 중일 때:
E2E_MODE=proxy E2E_ORIGIN=http://127.0.0.1:8444 pnpm test:e2e
pnpm build
E2E_MODE=production pnpm test:e2e
```

임시 프록시가 없으면 `E2E_MODE=proxy pnpm test:e2e`로 Next의 접두사 경로 처리만 검사할 수 있다. 이 경우 실제 프록시 경유 검증과 구분한다.

검증용 임시 프록시는 종료했다. 사용자 확인용 Next 개발 서버는 3000번에서 실행하며, `https://ide.hothyun.com/absproxy/3000/`에서 로그인한 IDE 세션으로 확인한다. 일반 터미널 실행과 장시간 미리보기의 재시작 절차는 [개발 환경](../engineering/DEVELOPMENT_ENVIRONMENT.md#개발-서버-유지와-접속-장애-점검)을 따른다.

Next.js가 `next dev` 실행 중 AGENTS.md에 추가하는 관리 블록은 설치된 `generate-agent-files.js`에서 출처를 확인했다. 프로젝트의 간략한 작업 규칙 뒤에 해당 블록을 보존한다.

## 2026-09-11 개발 접속 장애 복구

기존 3000번 Next 프로세스는 살아 있었지만 상태 API가 8초 동안 응답하지 않았다. 개발 로그에서 `write EPIPE`와 이전 의존성 재설치 시점의 Next 패키지 탐색 오류를 확인했다. 표준 출력은 이전 도구 실행의 파이프에 연결되어 있었다.

해당 앱 실행기를 종료하고 별도 세션·파일 로그 방식으로 재시작했다. 실행 명령이 끝난 뒤에도 서버가 유지되며, `/absproxy/3000/api/health`가 200으로 응답하는 것을 확인했다. 현재 로그는 Git에서 제외한 `.cache/dev-server.log`, 실행기 PID는 `.cache/dev-server.pid`에 기록한다.

기존 `tests/e2e/environment.spec.ts`를 재사용해 실제 3000번 서버에 `http://localhost:3000/absproxy/3000/`으로 접속했다. HTML·CSS·JS·내부 이동·새로고침·상태 API와 public 이미지·클라이언트 API·WebSocket·HMR 상태 유지 검사 **2개 통과**, 운영 전용 검사 1개는 의도적으로 제외했다. 테스트 소스는 변경하지 않았으며 임시 접속 설정은 `.cache/access-check.config.ts`에 두었다. 최초 검사에서는 컨테이너의 Chromium 경로 설정 누락과 기본 허용 대상이 아닌 `127.0.0.1` 접속을 수정한 뒤 통과했다.

외부 HTTPS 주소는 미인증 요청에 Cloudflare Access 로그인 302를 반환했다. 사용자 인증 이후의 실제 외부 접속 성공은 아직 검증하지 않았다. 이번 조치는 개발 서버 실행 방식과 운영 문서에 한정하며 앱 코드·경로 설정·외부 인증 설정은 변경하지 않았다.

## 아직 연결·검증하지 않은 범위

- 사용자가 준비하는 Vercel 프로젝트와 Firestore DB.
- 사용자가 요청한 KTO API의 현재 승인 상태·키·실응답.
- OpenRouter 크레딧 잔액·모델·실제 추출 정확도·토큰 비용. 이번 작업의 유료 API 호출은 0회.
- 실제 외부 `ide.hothyun.com`의 Coolify·TLS·인증 세션 경유 동작.
- 실제 배포 URL, 최종 도메인. 디자인 레퍼런스는 ref/로 수령하고 반영했다.

다음 연결 검증은 현재 키로 실제 KTO 원문 → OpenRouter 추출 → 판정·근거 흐름을 실행하는 것이다. 가상 체험·합성 공급자 테스트 통과를 공모전 필수 API 사용 완료나 실데이터 정확도 검증으로 표시하지 않는다.

## 제품 UI와 전체 과업 검증 (2026-09-11)

DESIGN.md 작성 후 ref/ 4장의 분위기를 반영한 한국어 랜딩과 여행 노트를 구현했다. 자체 호스팅 Pretendard, 반려견 사진과 SVG 순서 노선도를 사용한다. 여러 반려견·준비 상태·코스 검색/순서/구역/체류/고정 편집, 네 상태 결과, 원문 근거 dialog, 대체·되돌리기·전체 재검증, 중복 준비물 합치기, 문의 문구·인쇄, 명시적 기기 저장/삭제를 제공한다. 실제 모드 준비 부족과 가상 체험은 명확히 구분한다.

현재 64개 단위 검사, lint·타입·운영 빌드 통과. 데스크톱/모바일 각각 직접 개발·실제 로컬 code-server 프록시·운영 루트의 전체 Playwright 검사 합계 **36개 통과, 6개 의도적 제외**. 각 모드에서 개발 전용/운영 전용 검사 제외가 2개씩이다. 스크린샷은 test-results/, HTML 리포트는 playwright-report/에 기록한다. 외부 IDE의 사용자 인증 이후 접속이나 외부 Vercel 배포를 테스트한 결과는 아니다.

브라우저에서 발견한 Strict Mode dialog 재개방 시 닫힘, Next 라우트 안내와 오류 locator 충돌을 수정했다. 모바일 가로 넘침 없음, 키보드 Escape와 포커스 복귀, 조건 변경 후 stale 표시·재검증, API 장애 후 재시도, 원문 없는 기기 저장을 검사했다. 폰트·사진 라이선스와 출처는 src/assets/fonts/OFL.txt 및 public/media/CREDITS.md에 있다.

## 반복 실행 안정성과 검증 자동화 (2026-09-11)

`pnpm verify`로 단위 검사 64개, lint·타입·운영 빌드, Playwright 36개 통과·6개 의도적 제외를 최종 확인했다. 인쇄 시 날짜·반려견 정보 유지도 포함한다. 로컬 code-server 8444번을 실제 경유했으며 리포트는 직접 개발·프록시·운영별로 분리했다.

전체 검사를 재실행하면서 개발 프록시의 HMR 연결·API 상태는 유지되지만 변경 제목이 반영되지 않는 실패를 발견했다. 개발 파일시스템 컴파일 캐시를 끈 뒤 전체 검사가 통과했고, 별도 프록시 basePath 환경에서 데스크톱/모바일 HMR을 각 2회 더 반복해 **4개 모두 통과**했다. 후자의 추가 검사는 code-server 프록시 자체를 경유한 검사가 아니다. Next 내부의 근본 원인을 확정한 것은 아니다.

`pnpm preview:start` → 상태 API 200 → `pnpm preview:stop` → 포트 종료 → 다시 시작을 확인했다. 별도 세션·파일 로그로 IDE 미리보기를 유지하며 컨테이너 재시작 후 자동 복구를 보장하지 않는다. 사용자 레퍼런스 원본은 수정하거나 커밋하지 않았다. 실행 방법은 [검증 안내](../engineering/TESTING.md)를 따른다.

## shadcn 입력·디자인 시스템·상태 리팩터링 (2026-09-11)

날짜·시간·체류시간·구역을 shadcn 기반 Radix Select/Popover와 한국어 Calendar로 교체하고 초록 포커스 토큰을 적용했다. Button·Input·Checkbox·Dialog 등 공통 UI와 `/dev/design-system` 갤러리를 마련했다. 근거 모달은 Radix로 이전했다. Planner의 요청·저장·상태 처리를 hooks/store/panels로 분리했고, Zustand 스토어를 화면별로 생성하며 TanStack Query로 요청 생명주기를 관리한다.

최종 `pnpm verify`: **단위 테스트 70개, Playwright 60개 통과·6개 의도적 제외**, lint·타입·운영 빌드 통과. 브라우저는 데스크톱·모바일에서 직접 개발/실제 루프백 code-server 프록시/운영 모드 각각 20개 통과했다. 기존 코스 과업과 추가 입력·스토어·요청 동작을 검증했다. 디자인 시스템 갤러리는 개발에서 표시되고 운영에서 404다.

Select 키보드 검사에서 Home 이후 비동기 포커스 이동 전에 Enter를 보내는 타이밍 실패가 있었다. 설치된 Radix 소스의 지연 포커스를 확인하고 `toBeFocused()` 검증 후 Enter를 보내도록 수정한 다음 전체 검사가 통과했다. 자동 재시도는 0으로 유지했다. 모달 Escape/포커스 복귀, 연도 경계 날짜·00:07 시각·기존 75분 체류값, 비활성 입력, 중복 검사 방지, 모드 초기화·명시적 저장을 포함한다.

실제 API 키 연결·공급자 응답 정확도·요금·배포 성능 실측은 이 UI/구조 검증에 포함되지 않는다. 코드 경계와 상태 소유권은 [UI 디자인 시스템](../engineering/UI_DESIGN_SYSTEM.md)에 기록했다.

## 코드 품질 점검과 Sonner 작업 알림 (2026-09-11)

Sonner 2.0.8의 공통 Toaster와 `withNotifications` HOC를 Planner·개발 디자인 시스템에 적용했다. 타입이 있는 일회성 이벤트를 통해 저장·불러오기·삭제·검사·대체·되돌리기·방문지 편집·검색·복사 결과를 안내한다. 도메인·사용 사례는 Sonner에 의존하지 않는다. 화면별 호스트와 작업별 ID로 이전 알림만 닫고, 화면 이탈 후 결과는 새 토스트를 만들지 않는다. 자세한 결과·오류는 화면에 남긴다.

코드 점검에서 복사 실패의 상태 구분, 취소된 요청의 결과 반영, 프록시 HTML 응답의 파싱 오류, JSX에 있던 방문지 제거 액션을 보완했다. Playwright에서 발견한 닫기 직후 동일 ID 재사용의 알림 소실도 수정했다. 사라지는 이전 항목이 DOM에 잠시 남는 전환 특성을 고려해 알림 검사 범위를 현재 항목으로 지정했다. 초기 수정 후 직접 개발에서 저장·닫기·재저장 흐름을 데스크톱/모바일 각 5회, 총 10회 통과했다. 이후 전체 검사에서는 토스트 브랜드 색상 확인도 추가했다.

발견 사항과 변경 근거는 [코드 품질 점검](../engineering/CODE_QUALITY_REVIEW.md), 재사용 계약은 [UI 디자인 시스템](../engineering/UI_DESIGN_SYSTEM.md)에 기록했다. 실제 외부 API·배포 연결과 공급자 품질/비용 실측은 이번 검증 범위에 포함되지 않는다.

## Firebase 공통 인증·계정 여행 노트 (2026-09-12)

Firebase Web/Auth와 Admin/Firestore 초기화를 공통 모듈로 분리했다. 공개 Web 설정 4개와 서버 서비스 계정 설정 3개를 분리하고 지연 초기화하며, 키 없이 기존 비로그인 기능을 실행할 수 있다. Google 팝업·이메일 가입/로그인·인증 메일·비밀번호 재설정·로그아웃·인증 상태 복원을 구현했다.

서버가 ID 토큰·이메일 인증·사용자 상태를 검증하고 사용자 UID 아래 여행 노트를 저장한다. 제목과 기존 사용자 입력만 최대 20개 보관하며 Rules로 브라우저 직접 DB 접근을 거부한다. 목록·저장·수정·불러오기·삭제, 트랜잭션 개수 제한과 revision 충돌 확인을 구현했다. 로그아웃 시 계정 목록을 제거하고, 입력 교체 시 이전 판정과 대체 결과를 지운다. 기기 저장을 자동 업로드하지 않는다.

Firebase Auth/Firestore 에뮬레이터에서 직접 개발·개발 basePath 각각 **10개 통합 검사**를 통과했다. 인증/소유권/비활성 계정/직접 접근 거부/동시 저장 한도/버전 충돌, 브라우저 가입·인증·계정 변경·저장 실패·삭제 확인·비밀번호 재설정을 확인했다. 알림 종료 처리를 보완한 뒤 직접 개발 10개와 가입·저장 시각 흐름 2개를 재확인했다. 가입 Dialog와 계정 노트 패널의 데스크톱·모바일 스크린샷을 검토했고 로그인 방식 선택을 세이지 배경의 분할 버튼으로 정리했다.

최초 회귀 검사에서 320px 헤더 넘침을 발견했다. 설치 버튼을 아이콘으로 줄이고 좁은 화면의 보조 화살표·간격을 조정한 뒤 시각 스크립트의 320·360·390·768·1024·1440px 검사 모두 통과했다. 실제 화면 폭과 가로 넘침, 설치 모달, 홈 카드, FAQ, 콘솔 오류를 확인했다.

실제 Firebase 프로젝트 설정·키 입력·규칙 배포, Google 실제 OAuth와 인증/재설정 메일 도착·설치 PWA의 실제 기기 로그인은 아직 검증하지 않았다. 준비 순서와 환경변수는 [Firebase 설정 가이드](../engineering/FIREBASE_AUTH_AND_STORAGE.md), 재실행은 [검사 안내](../engineering/TESTING.md)에 있다.


최종 `PWA_ENABLED=true pnpm verify` 종료 코드 0: **단위 89개·일반 Playwright 150개 통과, 환경별 의도적 제외 6개**, lint·타입·운영 빌드 통과. 직접 개발·실제 로컬 code-server 프록시·운영 루트에서 각각 50개 통과했다. 위 Firebase 통합 검사는 별도 실행한 결과다. 전체 검증 후 PWA 미리보기를 다시 시작했다. 원격 푸시·배포와 실제 Firebase 프로젝트 변경은 수행하지 않았다.


## Firebase 실연결과 비밀번호 기준 정합성 (2026-09-13)

사용자가 Web 설정 4개·Admin 설정 3개를 입력한 뒤 실제 프로젝트의 인증과 Firestore 연결을 검사했다. 이메일 로그인·미인증/비로그인 차단·인증 상태 갱신·계정 노트 CRUD·새로고침 후 복원·로그아웃이 통과했다. 클라이언트 직접 DB 읽기·쓰기 403도 확인했다. 임시 Auth 사용자와 해당 UID의 문서를 모두 정리하고 삭제를 확인했다. 기존 사용자 데이터는 조회하지 않았다.

가입 입력 최소 길이, 안내와 약한 비밀번호 오류 문구를 사용자 Firebase 정책인 10자 이상으로 맞췄다. Playwright에서 해당 입력 제한과 안내를 확인했다. 재실행 절차는 [Firebase 가이드](../engineering/FIREBASE_AUTH_AND_STORAGE.md)에 있다. 실제 Google OAuth, 메일 수신·인증 링크, 설치 PWA 기기 검증은 남아 있다. 가상 코스 입력으로 저장 기능을 검사했으며 KTO/LLM 실제 호출 검사와 구분한다.

이번 변경은 단위 검사 **89개**, 린트·타입 검사·운영 빌드를 통과했다. 실제 프로젝트 브라우저 검사는 localhost 개발 basePath에서 완료했으며, 전체 일반/에뮬레이터 회귀 검사를 다시 수행한 것은 아니다.
